# Socratic method: how to guide in baby steps

This is the heart of the skill. The learner should reach each idea by their own reasoning, through questions so small that each one costs almost no effort, while the picture builds up one piece at a time.

## The principle: reasoning, not guessing

A question is only Socratic if the learner can answer it by **reasoning from things they already have**. There are exactly three legitimate sources for an answer:

1. **Everyday experience** (the floor).
2. **Nodes already mastered** in this session.
3. **Facts stated in the current message** (the "scene" or "given").

If an answer needs anything else, the learner can only guess, and a guess teaches nothing and feels like a quiz they are failing. Before asking, check that the answer lies within these three sources. If it does not, either add the missing premise to the scene or turn the node into a told node.

## Guided versus told: what can and cannot be elicited

Some things can be *reasoned out*; some can only be *told*.

| Reasoned out (guided) | Told (stated briefly, with its why) |
|---|---|
| Why a problem exists, and what kind of solution would fix it | Names and vocabulary ("this is called a port") |
| Consequences ("what happens if...?") | Arbitrary conventions (the number 80) |
| Why one design beats another, given constraints | Historical facts, dates, versions |
| How two ideas combine | Definitions of notation and symbols |
| The need for a convention | The specific value a convention took |

The learner can often derive the *need* for a convention and the *shape* of the solution, then you tell the arbitrary part, with the honest statement that it is arbitrary and why agreement matters. This keeps the Socratic benefit (they understand why) without pretending the arbitrary can be deduced.

Never withhold vocabulary or a fact as a "teaching moment". If the learner asks "what does X mean?", tell them at once, with its why, and move on. Socratic questioning is for reasoning, not for gatekeeping facts.

## Anatomy of a quest

Each guided node is a short sequence, called a quest:

1. **Hook (scene).** A concrete, small situation that uses only things the learner has. It makes the problem felt before the concept exists. Contains any needed given facts, each with its why.
2. **Ladder.** A chain of tiny questions. Each answer becomes the premise of the next. The chain ends at the *key insight*.
3. **Insight.** The learner states (or picks) the key idea. The agent confirms with the reason.
4. **Name and consolidate.** Only now give the concept its name and state it crisply (2-4 sentences, every statement with a why, plus where any analogy breaks).
5. **Check.** One tiny transfer question that uses the idea in a new, small situation.
6. **Map update.** The node turns green (or yellow if it needed heavy help), and the updated map is shown.

**Concept before label.** Always let the learner meet the idea before the word. A name attached to an idea the learner already holds is remembered; a name given first is just a sound.

A typical quest is 4-8 questions. If a ladder grows beyond about 8, the node is too fat: split it.

## Designing questions: the baby-step rules

1. **One idea per question.** If you are tempted to use "and", split.
2. **Small answer.** One word, a number, yes/no, a pick-between-two, or one short sentence. The learner should never need a paragraph.
3. **Start obvious.** The first question of a quest should be almost impossible to get wrong. It loads the scene, builds momentum, and tells the learner that this is easy-going. Obvious questions are not a flaw; they are the foundation of the picture.
4. **Ramp slowly.** Obvious, then a one-step inference, then the key insight (a *small* leap from the previous answer), then the transfer check. If the leap between two consecutive questions feels larger than "one small thought", insert a question.
5. **Chain the answers.** Reuse the learner's own words in the next question ("You said the address only reaches the building. So...") so they feel they are building the picture themselves.
6. **Concrete first.** Prefer scenes with letters, flats, queues, kitchens, shops, rather than abstractions. Label analogies as analogies and say where they break during consolidation.
7. **Answerable, always** (see the principle above).
8. **No tricks.** Never ask a question with a hidden catch, and never use a question to test whether the learner "knows" something they were not taught.
9. **Give the learner an easy out.** Encourage guesses ("a guess is perfectly fine"), accept short answers, and let them tap options when the answer space is small.
10. **Exactly one question per message.** Never stack questions. A single question mark keeps the thread clear.

**Effort balance.** The learner should feel like they are being walked along a path, with a small step each time, not examined. If a learner needs more than a few seconds to answer, the question is too big.

**Options.** For the smallest steps, offering 2-3 options lowers effort (use a tap-to-choose tool if the environment has one, otherwise A/B/C in text). Use options when the answer space is tiny and the point is the *direction* of thought. Use open answers at the key-insight moments, because choosing from options can hide whether the learner truly understood. Never make an option list so leading that only one is plausible.

## Question forms

Rotate between these so the dialogue does not feel mechanical:

| Form | Example shape | Good for |
|---|---|---|
| **Observe** | "Look at this situation. What do you notice?" (with something concrete shown) | Getting the picture loaded |
| **Predict** | "What do you think will happen next?" | Surfacing intuition and misconceptions |
| **Choose** | "Which seems more sensible: A or B?" | Direction of thought, very low effort |
| **Complete** | "So the letter reaches the ____" | Tiny recall of just-established ideas |
| **What-if-removed** | "What would go wrong if this part were missing?" | Revealing why a piece exists |
| **Spot the problem** | "Here are two programs waiting on the same door. What problem?" | Motivating a concept |
| **Compare** | "How is case 1 different from case 2?" | Distinguishing ideas |
| **Order** | "Which comes first?" | Sequences |
| **Transfer** | "Now a new case: what happens here?" | The mastery check |
| **Why-probe** | "What makes you say that?" | After a correct answer given without reasoning |

## Bad questions and their fixes

| Bad | Why it fails | Fix |
|---|---|---|
| "What is a port?" | Asks for a definition the learner has no basis for | A scene, then "what extra information would the sender need?" |
| "Why do you think the designers chose 80?" | Guessing at arbitrary history | Tell it; ask about the *need* instead ("how would a browser know where to knock?") |
| "What are the differences between TCP and UDP, and which would you use?" | Many ideas, huge answer | Split into tiny questions across nodes |
| "Don't you think it would be better if...?" | Leading and low-information | A neutral "which is more sensible, A or B?" |
| "Is it true that X?" (a coin flip) | A 50% guess shows nothing | Ask "what would happen if X?" or add "why?" afterwards |
| Questions that use an untaught term | Not answerable | Teach or define first, or rephrase in plain words |
| Rhetorical or quiz-show tone | Feels like an exam | Warm, short, curious |
| Two questions in one message | Derails the thread | Keep the better one |

## The hint ladder

When the learner is stuck, escalate through small steps. Never leave them failing; two stuck attempts at one level means go up one level.

| Level | Move |
|---|---|
| 0 | The question as asked |
| 1 | **Narrow it:** rephrase in simpler words, or add one concrete detail to the scene |
| 2 | **Offer options:** "is it closer to A or B?" |
| 3 | **Half-way:** state the first half of the reasoning ("if X is true, then Y follows") and ask the last tiny step |
| 4 | **Tell it, with the why:** state the answer and its reason, then ask a very small confirming question that uses it |

"I don't know", "tell me", or "just explain" should jump directly to level 4, without any pressure or guilt: being told is always allowed, since the goal is understanding, not performance. Record the hint level reached; heavy help changes the node's status (see mastery).

## Feedback

Keep feedback short (1-3 sentences) and always followed by the next question.

- **Correct:** confirm *and give the reason*, in the learner's own words where possible. "Yes, because the street address only reaches the building, and nothing in it says which app."
- **Partly correct:** keep the correct part, name what is missing, and ask a smaller question about the missing piece.
- **Wrong:** do not say "wrong". Treat the answer as a sensible reading of the information they had: "That would be true if ___. Let's test it on this case:" and give a small scenario where their idea breaks, asking what happens. Let them discover the contradiction. Never pile several corrections in one message.
- **Right for the wrong reason:** ask one why-probe before moving on.
- **Correct but hesitant:** a short confirmation is enough; do not over-praise.

Keep the tone warm and matter-of-fact. Avoid heavy praise ("Great job!!") and avoid "obviously", "simply", "just", because they make the learner feel slow when a step felt hard.

## Naming and consolidating

After the key insight, close the quest with a short consolidation:

- Give the **name**, with the reason for the name.
- State the idea in 2-4 sentences, **each with its why**, using the learner's own formulation as the core.
- If an analogy was used, say where it stops being accurate.
- State what it **unlocks** (which later node needs it), so the learner sees where it fits on the map.

Keep it short. The learner already did the thinking; the consolidation just fixes the result in precise words.

## Mastery, shaky nodes, and spaced recall

A node is `done` (green) when the learner answered the key-insight question and the transfer check correctly with no hint above level 2.

A node is `shaky` (yellow) when it needed level 3 or 4 help, or the transfer check failed once and was repaired. Shaky nodes are not failures. They are scheduled for a **spaced recall**: one tiny recall question at the start of the next quest that depends on them (and again later if needed). If the learner answers it comfortably, upgrade to `done` and recolour in the next map.

Do not drag a learner back repeatedly for a node. One consolidation, one check, one scheduled recall at most.

## The quest card

Prepare one card per guided node (write the first few during planning; write the rest just before they are needed, so the dialogue adapts to this learner):

```
Node: <id, name>            Mode: guided | told
Target insight: <the one idea the learner must reach, in plain words>
Uses (premises available): <mastered nodes + floor items used>
Scene: <the concrete situation, 1-3 sentences>
Given facts (told, each with why): <only what cannot be deduced>
Ladder (beats): 
  1. <purpose> -> <tiny question> -> <expected answer>
  2. ...
  k. KEY INSIGHT question
Likely wrong answers and probes: <answer> -> <scenario that exposes the contradiction>
Name to give after the insight (and why it is called that): <...>
Consolidation (draft, whys included): <...>
Transfer check: <tiny new-situation question> -> <expected answer>
Unlocks: <later nodes>
```

The card guarantees that the quest is *answerable* and *on target*. During the dialogue it is a map, not a rail: if the learner answers ahead of the question, skip the beats that become redundant.

## Worked example: "Port"

Context: node 4 (IP address) is mastered: "an address identifies one machine on the network". Floor: everyday life. Node 5, Port: target insight is "one machine runs many programs, so the address needs a second label that picks the program, and that label must be a pre-agreed kind that senders can know without asking".

Annotations in brackets are for the agent, not for the learner.

---

*Node 5 · Port - question 1 of ~6*

Your computer has one IP address, like a building has one street address. On that computer, a browser, a mail app, and a music app are all waiting for messages at the same time.

**Q1.** A message arrives with just your street address on it. Can it tell the computer *which app* should get it?

[Obvious. Expected: "no". Purpose: establish the problem.]

> Learner: no

Right, because the street address only gets the message to the building; nothing in it names an app.

**Q2.** So what extra piece of information would the sender need to add to the message?

[Predict. Expected: "app name / which app / apartment number".]

> Learner: the name of the app?

That's a sensible first idea, and it would work if the sender knew which apps you have. Let's test it.

**Q3.** Could someone sending you a message from the other side of the world know which apps you installed?

[Spot the problem. Expected: "no". This is the gentle counter-scenario for the wrong-ish answer.]

> Learner: no

Exactly, because they have never seen your computer, so a label based on your own apps could never be known in advance.

**Q4.** So the label has to be something *everybody* can agree on beforehand, without looking at your computer. A long list of names, or a short number?

[Choose. Low effort. Expected: "number" (accept a reasoned "list" and discuss: numbers are shorter and need no spelling or language.)]

> Learner: a number, shorter

Yes, a number is short and has no spelling or language problems, which is why it suits a label every computer must understand.

[KEY INSIGHT reached. Name and consolidate.]

That number is called a **port**, like a gate through which messages enter the building and reach the right app. So: the IP address gets a message to the right *machine*, and the port number gets it to the right *program* on that machine, because one machine can run many programs at once. (The building analogy breaks in one place: the "flats" are not physical, they are just numbers the computer assigns.)

**Q5.** Now a web browser knows only a website's name. It has to connect to that site's server. Which port should it try, and how could it possibly know?

[Predict. Expected: "ask the server" -> next beat shows the circularity.]

> Learner: ask the server which port?

**Q6.** But to ask the server, the browser already has to talk to it, and to talk to it, it needs the port. What does that tell us about the number?

[Spot the problem. Expected: "it has to be known in advance / agreed".]

> Learner: they have to agree on one beforehand

Yes, because otherwise the browser could never make the first contact. So web servers wait at a pre-agreed default number, 80. The digits 80 themselves are arbitrary: it is simply the number registered for web traffic, and it works because every browser and server follows the same agreement, since a server on a different number would be unreachable by default.

**Q7 (check).** A friend runs a music server and a web server on the same computer. Both receive messages at the same IP address. How does the computer know which one a message is for?

> Learner: the port number

Yes, because each program waits at its own number. ✔ node 5 is done.

[Updated map shown here with node 5 green, and the next node's scene and first question follow in the same message.]

---

Note what happened: the learner reasoned out the *need* for a second label and the *need* for a pre-agreed default; the agent *told* the name and the arbitrary number, each with its why; every question was tiny and answerable; the agent never lectured, and no side question was needed.

## Quick checklist for every question

- [ ] Answerable from the floor, mastered nodes, or facts in this message?
- [ ] One idea, one question mark?
- [ ] Answerable in a word, a number, a pick, or one short sentence?
- [ ] Does it have a purpose in the quest card, and does it move toward the key insight?
- [ ] Is the leap from the previous answer small?
- [ ] Is the previous answer's feedback short, with its reason?
- [ ] Would a tired learner still find this easy to answer?
